# Terminal file delivery

Ordinary and Tether terminal attachments default to the WebUI upload path. An explicit filesystem
preference enables copying to that selected terminal. File panels keep the actor, chat, model and terminal
instance bound to each request. Native Agent delivery uses attachments on the current outgoing turn only.
Managed connections use a 0.4+ orchestrator and require manual rebinding during this upgrade.
The orchestrator selects the instance from the template, user, chat and model headers. WebUI keeps
its resolved instance identity for authorization, signed file links and previews.
See [connection and upgrade decisions](upstream/v0.13.4-decisions.md).

Admin-configured terminals can deliver generated files through authenticated links in chat.
`display_file` adds `download_url`, `owner_id`, and (for supported images) `image_url` after the
terminal confirms that the file exists. The model should copy these URLs into Markdown links
and images. The terminal file browser gets the same fields through `files/display`.

The delivery endpoints are:

- `GET /api/v1/terminals/{server_id}/files/download?ref=...`
- `GET /api/v1/terminals/{server_id}/files/image?ref=...`

Links generated by `0.13.4+f1` bind the generating user, terminal ID, absolute path and resolved
terminal context. Managed templates also carry the request's model and delegated instance owner when
present. A keyed digest (HMAC) binds the resolved terminal endpoint while keeping its address and
credentials private. Pointing the same connection at a new address invalidates those links.

Links issued before the upgrade keep their original user, terminal, path and context checks. Every
download requires the generating user's login, checks current terminal and chat access, and resolves
terminal authentication again. A recipient of a shared chat needs their own authorized file link.

Files are read from their original terminal path on each request. There are no stored copies,
database records, or independent link expiry. Replacing a file changes the delivered content;
deleting the file, losing access, changing the configured runtime context, or rotating
`WEBUI_SECRET_KEY` makes the link unavailable. Temporary chats retain the original terminal context
as described below. Personal direct terminal connections keep their download behavior, but the
Direct Integrations switch disables saved personal tools and terminal connections for everyone,
including admins. Configuration is retained for re-enabling; admin server connections are separate.

## Content isolation

Downloads always use `application/octet-stream` and `Content-Disposition: attachment`, including
HTML, JavaScript, PDF, and SVG. PDF and Office previews continue through client-side parsers.
Downloads stream without a file-size cap and close their upstream connection on completion or
interruption. The proxy uses a 10-second connection timeout and a 60-second idle read timeout.

Image previews accept PNG, JPEG, GIF, WebP, and SVG after checking the actual bytes. Image validation
buffers at most 32 MiB plus one overflow byte; larger images return 413 and remain downloadable.
Invalid or unsupported images return 415. SVG must have the SVG namespace/root, no DTD or XML
processing instructions, and pass XML parsing with entity resolution and network access disabled.

SVG previews use an `<img>` pointing at the protected HTTP URL. Source views show escaped text;
the application does not insert SVG file markup into the page. The response also carries an
unprivileged CSP `sandbox`, denies scripts, connections, frames, and forms, and permits only internal
styles and embedded image/font data. These response headers protect direct navigation as well as
image previews. See [SVG image restrictions](https://developer.mozilla.org/en-US/docs/Web/SVG/Guides/SVG_as_an_image)
and [CSP sandbox](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/sandbox).

All terminal file responses disable caching and MIME sniffing, restrict cross-origin embedding,
and reject browser cross-origin subresource requests (including CORS requests). They
discard untrusted upstream security headers, cookies, refresh headers, and redirects. The old
`files/view` and `files/serve` entry points apply the same content policy. Same-origin terminal
`proxy/{port}` web previews are disabled; HTML is available as source or a download. Terminal
control JSON/SSE and interactive sessions remain available. This policy is confined to terminal
content routes.

## Opening files in chat

A signed `display_file` result appears as an inline card. Its preview, source view (where supported)
and download use the signed file's original chat or automation context. The card omits the
open-in-file-browser action because the current chat can point to a different workspace.

With tab display selected, a path-only `terminal:display_file` event opens or reuses a background
file tab in the originating chat on the selected terminal, preserving the requested page and the
active tab's focus. Click the file tab to view it. The inline display preference keeps files in the
message. When the prompt has a filesystem attachment, the event only refreshes a matching open preview.

Admins can enable **Show Files on Terminal Select** under **Admin Settings → Integrations → Terminal**.
The environment default `SHOW_FILES_ON_TERMINAL_SELECT` is false and the saved setting is
`terminal.show_files_on_select`. When enabled, selecting a terminal on desktop (at least 1024 px
wide) opens its file list for any user with terminal access. A `run_command` event refreshes only
existing directory tabs on the selected terminal, preserving their paths and focus. Commands with
a filesystem attachment or a selected file preview skip that directory refresh.

## Per-chat operations and comparisons

With a terminal configured for per-chat workspaces, file reads and source/comparison reads, edits,
new files, notebook execution, batch deletion and ZIP downloads carry the current chat ID. Comparison
reads use the same terminal and chat as the selected files. Switching chats must not reuse content
from a previous workspace. File saves retain their version/concurrency checks where supported.

Connection/chat changes cancel or discard late directory and source-read results. Notebook kernels
created by a stale request are cleaned up using their original connection/context. A revision
comparison also verifies that the draft and selected version have not changed before applying it;
opening a comparison does not reserve the editor or authorize overwriting a later edit.

These operations still require current terminal and chat access. Signed delivery links continue to
resolve their original context, independently of the currently open chat. HTML is source/download
content and SVG previews remain isolated; the new file actions do not enable same-origin port previews.

### Editing and Git

Open a writable text or code file in a file tab to edit and save it in the selected workspace.
When the file changes on disk during editing, the editor asks before overwriting it. A failed
save keeps the draft in the editor. A chat, account or connection change invalidates the previous
save target.

On terminals with Git support, the file tree shows working-tree changes and the editor can show
staged or unstaged diffs. The Git controls operate on the repository in the selected terminal
and chat context. They include staging, commits, branches and worktrees. Clone uses the selected
directory.

### Browser tabs and port previews

In the main chat, a model can call `browser_open_tab` to open a blank tab when the selected
Open Terminal provides `browser_action`. The result identifies the new browser `session_id` and
mode. In Chrome mode, reuse that ID with `browser_action` to navigate, read or click in the same
tab. A Proxy result explains that interaction requires Chrome. If creation is unconfirmed, check
`browser_tabs` for an existing session before opening another.

Proxy mode and embedded port pages require an independent preview hostname configured by the
administrator. The embedded page runs in a sandbox with no access to WebUI's DOM or browser storage.
Preview tickets are bound to the current login, terminal and chat context and expire after five
minutes. WebUI rechecks access during active use. The existing file source, download and image
preview actions remain available under the terminal file policy.

See [independent terminal previews](terminal-preview.md) for setup and browser behavior.

## Temporary V2 contexts and saved artifacts

A V2 temporary chat uses its server-issued context ID and epoch, independently of its socket ID.
File browsing, comparisons, edits, notebook operations and interactive terminal sessions carry
that identity together with the original admin connection and `temporary:<id>` chat context.
HTTP requests use `X-Temporary-Context-Id` and `X-Temporary-Context-Epoch`; the WebSocket path
passes the corresponding authenticated query values. Guessing a chat key or reusing a socket
does not authorize another temporary workspace. Every operation checks the current actor and
scope; missing, closed, expired or unavailable context state fails explicitly.

The page captures the actor, connection and context for each operation. Changing accounts,
connections or chats discards late reads and does not send a stale save to the new workspace.
Cleanup of an already-created notebook or terminal session uses its original identity; this
limited cleanup path does not permit new reads or execution after closing the page.

Signed `display_file` links have a different lifetime from live browsing. Their verified
signature retains the generating user, original connection, path and temporary context. Closing
the temporary cache or converting the conversation to a saved chat does not redirect those links
or invalidate them solely because the cache is gone. Requests still require the original actor,
current terminal access and the signed origin. Another user cannot gain access by receiving an
export or shared chat. Changing the current connection never changes an existing link's target.

Closing a temporary chat does not delete files on the terminal. Conversion/export preserves raw
tool calls, results and signed links while removing temporary compaction/selection identities.
The temporary scope is released only after successful saving and confirmed task completion;
failed saving keeps the page available. See the [temporary V2 lifecycle and storage guide](temporary-context-v2.md).
Content isolation and the prohibition on same-origin port previews apply to all these paths.

## Verification

Run with the development dependencies and Python 3.11/3.12, Node 22:

```sh
python -m pytest backend/tests -q
npm run test:frontend -- --run
npm run check
```

The terminal policy/router tests isolate auth, storage, and upstream transport to avoid application
database side effects. Browser validation should use the real frontend components and HTTP router,
with synthetic users and files: normal SVG styles, scripts and event handlers, foreign content,
external resources, DTD/entity declarations, and masquerading HTML. Check chat images, expanded
images, file-browser source/preview, and direct navigation in Chromium and Firefox. Verify owner
access, denial for copied/shared links, original-context binding, download bytes, and document
previews against the deployment's configured terminal/auth modes as well.

For scoped temporary regressions, start with `test_temporary_terminal_context.py`,
`test_terminal_file_routes.py`, the terminal API context/notebook tests and
`Chat.temporary-terminal.test.ts`. The [development guide](DEVELOPMENT.md#v0124-integration-and-temporary-v2-verification)
describes isolated environment setup and the wider acceptance map. Separate real terminal service
checks from tests that substitute its transport.
