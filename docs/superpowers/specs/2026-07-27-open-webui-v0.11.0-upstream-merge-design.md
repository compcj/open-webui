# Open WebUI v0.11.0 上游合并设计

## 背景

目标仓库是 `compcj/open-webui`，目标分支是 `main`。该分支当前基于
Open WebUI `v0.10.2` 的提交 `ecd48e2f718220a6400ecf49eafd4867a38feb10`，
并包含两个 fork 专属提交：

- `876d80e2a713c7d0ab27202a6d5df78827452a0b`：增加 Search1API Web 搜索支持。
- `7d1c161e78934ae42e2e7252c0e3687d743e620a`：合并 Search1API 功能分支。

待合并的上游版本是 `open-webui/open-webui` 的 `v0.11.0`，标签提交为
`f9590b8017199e56d5e953657e6498e3cef1d246`。GitHub 比较结果显示，fork
相对共同基点有 2 个提交，而上游标签相对共同基点有 616 个提交。

## 目标

在不重写 fork 历史、不强制推送的前提下，把上游 `v0.11.0` 的完整文件树
和历史关系合并到 `compcj/open-webui:main`，同时完整保留并适配 Search1API：

- `SEARCH1API_API_KEY` 环境变量和持久化配置。
- Search1API HTTP 搜索实现、结果标准化和域名过滤。
- Web 搜索引擎路由与缺少 API Key 时的错误处理。
- 管理界面的 Search1API 引擎选项和密钥输入框。
- Search1API 定向自动化测试。

## 合并策略

创建一个普通的双父合并提交：

1. 第一父提交是执行时重新读取的 `compcj/open-webui:main`。
2. 第二父提交是上游标签 `f9590b8017199e56d5e953657e6498e3cef1d246`。
3. 结果文件树以 `v0.11.0` 为基线，再将 Search1API 功能适配到上游的新结构。

优先通过本地 Git 合并生成该提交。如果 GitHub 大型仓库的网络获取持续失败，
则使用 GitHub Git Data API 创建相同文件树和相同双父拓扑的提交。两种方式都必须
满足以下条件：

- 不使用 rebase 或 force push。
- 推送前验证远端 `main` 没有出现未纳入合并的新提交。
- `main` 的更新必须是从执行时远端头提交出发的快进更新。

## Search1API 适配边界

需要以 `v0.11.0` 的实际接口为准检查并修改以下职责对应的文件：

- 后端配置：环境变量读取、持久配置键、请求配置对象和更新接口。
- 搜索实现：异步 HTTP 会话、认证头、请求负载、响应字段兼容、结果数量限制和域名过滤。
- 搜索路由：引擎注册、API Key 校验及调用约定。
- 前端设置：引擎枚举、配置模型和敏感密钥输入控件。
- 测试：请求参数、结果标准化、允许/阻止域名过滤、空结果、HTTP 错误和缺少密钥。

如果 `v0.11.0` 已改变搜索提供商的模块边界、配置访问方式或前端组件结构，
Search1API 应迁移到新模式，不能通过保留 v0.10.2 的整段旧文件来覆盖上游实现。

## 冲突与错误处理

- 对 fork 未修改的文件，直接采用 `v0.11.0` 文件树。
- 对 Search1API 涉及的文件，基于 `v0.11.0` 内容做最小增量修改。
- 上游已有同名配置或提供商时，先核对语义；不得生成重复配置键、重复选项或不可达分支。
- 任何无法确认的接口变化都必须在更新 `main` 前停止，不得以未测试的猜测推送。
- 若远端 `main` 在工作期间发生变化，重新比较并重建合并提交。

## 验证

更新远端 `main` 前至少完成：

- 确认结果版本是 `0.11.0`。
- 确认提交具有 fork 头和上游标签两个父提交。
- 运行或通过等价 CI 执行 Search1API 定向测试。
- 对修改的 Python 文件执行语法或静态检查。
- 对前端执行 Svelte/TypeScript 检查。
- 在依赖和运行环境允许时执行生产构建。
- 搜索冲突标记，确认结果中不存在 `<<<<<<<`、`=======` 或 `>>>>>>>`。
- 比较结果文件树，确认 fork 专属差异只包含 Search1API 适配及本次设计/计划文档。

如果本地网络无法取得完整源码，则先构造候选提交到临时引用并使用 GitHub Actions
验证；只有检查成功后才能把 `main` 更新到候选提交。若仓库现有工作流无法覆盖上述
检查，则不得仅凭提交创建成功宣称合并完成。

## 发布与回退

最终使用普通快进方式更新 `compcj/open-webui:main`，不创建强推。由于结果是普通
合并提交，出现问题时可以通过一个后续 revert 提交撤销合并，不需要重写分支历史。
