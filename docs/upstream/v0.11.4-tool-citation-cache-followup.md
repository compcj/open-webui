# v0.11.4 后续修复：工具引用与输入缓存

## 状态与范围

2026-10-10：已完成本地实现与针对性回归。供应商缓存读取量、写入量和费用尚未实测。
本记录是 [D05](v0.11.4-decisions.md#d05--摘要也可以编号引用保留差异) 的后续来源放置决策，
保留搜索摘要、导航结果、正文摘录的证据区别及混合来源编号策略，不改写原发布记录的历史验收。
本次不调整 OpenRouter 会话路由、缓存参数、模型选择或缓存有效期，无数据库迁移和新增依赖。

## 问题证据

用户在 OpenRouter 用量详情中观察到大量联网工具续答请求未命中输入缓存。代码追踪和合成复现发现：
每次产生新引用来源，原生工具循环都会恢复系统/用户消息，再将累计的 `<tool_sources>` 和文件 RAG 上下文
重新注入前面的消息。相同会话的系统消息因此持续变化。关闭引用的对照保持稳定。
这证明了应用端的前缀变化，不能单独证明某次供应商请求未命中的全部原因。

实施前的回归测试还发现：没有文本间隔的两轮工具调用在回放时被合并进同一条 assistant 消息，
导致上一轮的 `tool_calls` 随后续调用增长。两项测试均在修改实现前失败，分别指向系统消息和调用分组。

## 选定方案与兼容性

固定引用规则在初始请求准备阶段进入系统消息；新来源随产生它的工具结果追加。
工具循环不再恢复系统/用户消息、累计重建 `<tool_sources>` 或重新注入文件 RAG。
初始文件及非原生注入上下文保留原有处理方式；后台任务与子代理使用的已解析系统提示词元数据继续保留。原生搜索也使用现有来源解析器，以保留 D05 的摘要引用契约。

`function_call_output` 增加两个可选内部字段：

| 字段               | 含义与生命周期                                             |
| ------------------ | ---------------------------------------------------------- |
| `citation_context` | 首次生成的引用文本；保存后原样回放，不因新增来源重新渲染。 |
| `citation_sources` | 用于来源事件和恢复编号的结构化来源；不直接发送给供应商。   |

`output` 保留原始文本和图片。发送时在副本上附加引用文本；Chat Completions 与 Responses 的消息转换和
原生存储项回放均处理这一步。缺少新字段的旧记录保持原有行为。前端继续接收 `source` 事件和结构化输出，
无需新接口、设置或重新生成引用文本。

编号以当前 assistant 回复中首次出现的来源为准。恢复时优先读取当前回复保存的 `sources`，再补充输出项
的引用元数据；同一 URL/来源身份复用编号，同名不同 URL 保持独立。新回复有自己的编号空间。
原生执行与审批恢复共用引用附加逻辑；审批只刷新当前回复的输出投影，保持推理数据与并行调用的关联，
保留已准备好的系统提示、历史及附件上下文，包括具有同一 V2 消息 ID 的附加证据。投影位置在消息外记录，
临时标记在模型分发（含 Pipe）前移除。恢复流式处理前重新读取保存的回复，避免使用审批前的来源快照。
回放保留每一轮调用/结果边界。同轮多个调用仍成组，后续轮次不会重写旧的 `tool_calls`。

无状态请求重放已有内容并追加新结果。有状态 Responses 使用 `previous_response_id`，只发送本批新增结果，
保持系统 instructions 不变；V2 沿用无状态发送策略，以便计算和处理完整输入。图片与同模型推理数据
保持各自原有转换规则。

引用文本在输入预算与压缩前进入消息。启用 V2 工具预算时，新引用只保存 ID、类型和 URL 等标记，避免
在预算范围外重复正文；保存后不因模式切换重新生成。V2 工具预算引用范围只覆盖原始结果文本，摘要/摘录替换该范围时
保留引用后缀；精确原文读取不包含这个后缀。实际压缩历史、改变系统提示或工具定义仍可能改变缓存前缀。
